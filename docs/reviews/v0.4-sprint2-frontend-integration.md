# Writer Agent V0.4 Sprint 2 — Frontend/API integration

## Delivered scope

- Added a typed API adapter for the implemented V0.4 Workspace and Chapter
  routes, with runtime Zod parsing and explicit DTO mappers.
- Kept API revision IDs and content hashes opaque; Demo's numeric revision
  counter remains confined to Demo mode.
- Loaded the project workspace, real Harness chapter tree, and chapter Markdown
  on selection. An API project with no projected chapters displays an empty
  state and does not seed sample prose.
- Saved chapter Markdown as an immutable application draft using
  `baseRevisionId` compare-and-swap and a stable retry `Idempotency-Key`.
- Persisted workspace theme and layout preferences through the Workspace API.
- Added per-project/per-chapter local recovery drafts, retry, export, explicit
  server reload confirmation, stale-draft recovery, and 409 conflict blocking.
- When browser storage rejects a write, keep the exact current Markdown in
  memory, block the API request, and offer a direct export while warning before
  page exit.
- Recovery drafts have their own `有待恢复草稿` save state. The word count reads
  from the active TipTap document after recovery and ignores destroyed editor
  instances during chapter switches.
- Kept review, chat, challenge, knowledge, and proposal interactions in Demo
  mode only. API mode reports these features as unavailable and does not call
  their proposed endpoints.
- Added a local API + web launcher, API adapter/controller unit tests, and an
  end-to-end flow using isolated Harness fixture files and temporary server
  state.

## Author and Harness boundary

Chapter revisions are application drafts, not Harness writes or Git commits.
The author remains responsible for chapter prose and for separately committing
accepted work. The API adapter contains no Agent Runtime or LLM call. End-to-end
fixtures live under `apps/web/e2e/fixtures/harness`; the test does not modify
the repository's `manuscript/`, `book/`, `proposals/`, or `decisions/` data.

## Figma follow-up

The current frontend keeps the existing V0.3 visual system. Sprint 2 adds only
the minimal loading, recovery, unavailable-feature, and conflict notices needed
to safely use the already implemented API. The detailed conflict-resolution
experience remains open product design question OQ-030 in
`docs/reviews/v0.4-contract-review.md`: Figma should define conflict states,
available actions, and their visual treatment before that flow is expanded.
No automatic Figma listener or bidirectional synchronization is claimed.
