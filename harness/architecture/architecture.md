# 架构评估与决策

日期：2026-09-25。范围：单作者、AI 管理并提供启发，正文由作者书写。

## 决策
v0.1 使用 Markdown harness + Git + 任意文件型 Agent。暂不开发 pi SDK 应用。pi CLI 也可以作为这个文档体系的执行器，两者并不互斥。

| 维度 | 文档 harness | pi SDK 应用 |
| --- | --- | --- |
| 初期成本 | 维护约定和资料即可 | 要维护运行时、工具、模型接入、错误恢复 |
| 跨编辑器 | 高，显式读取入口即可 | 需要额外接入或服务界面 |
| 作者控制 | diff、提案和逐项确认直观 | 可做确认界面，但需要实现 |
| 硬性权限 | 提示词只是约定，不能保证 | 可在工具层实施路径与动作权限 |
| 重复批处理 | 人工启动，长任务容易遗漏 | 可队列化、重试、断点恢复 |
| 检索规模 | 索引与文本搜索，按章载入 | 可增量索引、全文搜索、检索过滤 |
| 持久状态 | 显式文档与 Git | 会话数据库与文档需保持一致 |

## Harness 的职责
入口约束 + 按任务取上下文 + 文件状态 + 操作流程 + 可追溯证据 + 人工决策 + 评估反馈。
它不是把所有资料塞进 AGENTS.md。模型的上下文和聊天压缩不能替代书籍档案。

## 数据流
作者创意/正文 → 原文保留 → 客观提取和审查 → 候选提案 → 作者逐项决定 → 正式资料与索引 → 下次写作准备。
外部作品 → 有出处的案例 → 表达机制比较 → 启发问题；不直接进入小说事实库。

## 边界和风险
Markdown 不提供强制访问控制；有写权限的 Agent 仍可能误写。使用编辑器权限限制、工作副本与 Git diff 检查；不要将 AGENTS.md 当作安全沙箱。正文备份与提交前 diff 是最低保护。
多模型同一时间仅一个写入者；若需并发，使用独立分支/工作树，人工合并后检查资料一致性。
索引与摘要可能过期：提取带内容 hash，接受前核对正文；读者分析需回到原文。
不设 AI 自动发布章节、自动决定剧情或自动演化作者风格的闭环。

## 何时升级
先以 5–10 章验证：维护是否减少作者负担，是否频繁遗漏引用/线索，是否需要无人值守批处理。
只有明确出现重复需求再增加：
1. Python/Node 静态检查：断链、重复 ID、失效 hash、待回收线索。
2. SQLite FTS 增量检索：以文件为事实源，可重建索引；先不用向量库。
3. pi 执行层：维护、审查、研究工具分别限权，正文只读，提案与正式资料分开写入口。

未来工具建议：read_context、search_evidence、write_proposal、review_consistency、apply_accepted_items。apply 工具验证作者选择、源 hash、允许路径并以单次事务写回。加入幂等键、任务日志、失败恢复、模型费用上限；文件格式和 ID 保持兼容。

## 评估
硬指标：正文未授权修改 0 次；正式设定未确认写入 0 次；已核验引用可追溯率 100%；种子矛盾检出率与误报率分别统计。软指标：意图理解获作者认可、表达案例有启发、维护耗时下降。不能用模型自评分替代作者判断。
