## 设计背景与原则

- 当前权威设计源：Figma Make [`Writer Agent UI/UX Design`](https://www.figma.com/make/kWBOdcae5utBZ6VtBHHXui/Writer-Agent-UI-UX-Design)，fileKey `kWBOdcae5utBZ6VtBHHXui`，入口节点 `0:1`。
- Codex 于 2026-10-14 通过 Figma MCP 读取了 IA、screen map、design system、写作工作台和功能说明。Make 未提供版本号；截图端点不支持 Make，因此未完成像素对照。
- 当前原型是 React + TypeScript + Tailwind + TipTap；源码中存在三栏工作台、章节导航、四个 Agent Tab、知识/提案入口、演示状态。产品说明也明确部分模块仍为原型或待议，不能设计成已接入真实后端。
- 产品底线：正文归作者；AI 只在作者主动请求后辅助理解与判断；不生成、覆盖或发布完整正文；非正式笔记不是作品事实；正式设定变更必须经过作者明确确认；Markdown + Git 是正式作品事实来源。
- 当前工程临时行为：无明确布局偏好时收起右侧 Agent 面板，保留章节导航；如果作者有已保存布局则恢复。此为降低干扰的渐进实现，不代表最终布局决定。

请先探索三种 IA，再确定 VNext：

1. 现有三栏工作台。
2. 正文画布 + 按需打开章节/Agent 面板。
3. 正文 + 轻量页边注记，“书”和“思考”作为二级空间。

重点检查初次开始写作成本、章节切换、审查发现定位效率、长时间写作的干扰、窄屏适配和作者对注记密度的感受。不要为了追求新颖默认采用方案 3。

## 任务 1：写作优先的工作台和信息架构

### 当前体验问题

- 当前原型导航同时展示章节、知识、提案/决策、Agent 工作台；右侧又有审查、对话、推演、决策 Tab。部分入口可互达，功能名称层级混杂。
- 现有 Figma 描述的是三栏工作台。Codex 的过渡代码已收起首次使用的右侧 Agent 面板，但正式 IA 尚未改版。
- 章节切换效率很重要，不能因“安静”目标而隐藏正在写哪一章或让章节入口难以发现。

### 建议流程

打开作品 → 明确看到当前章节与正文 → 需要时主动打开辅助空间 → 完成后可收起并回到正文。首次打开显示真实空项目状态；不虚构章节、不生成开篇。

### 页面/组件结构候选

- 写作：当前章节、章节导航、正文、保存/冲突状态、专注模式。
- 书（二级空间）：确认知识、人物、世界观、伏笔、变更历史、全量搜索。
- 思考（二级空间）：作者主动发起的讨论、审查、推演和发现。
- 辅助侧栏可探索“注记 / 思考”，避免在顶部再并列一排 Agent 管理入口。

以上标签和空间归属是候选，请 Figma 给出至少一个可点击方案并说明另两个方案的取舍。不要把未实现页面画成“已连接”。

### 交互状态

- 首次打开、已有偏好恢复、空作品、章节加载、已保存、有未保存修改、保存中、保存失败、409 编辑版本冲突、草稿恢复、只读原文保护。
- 左导航展开/收起、辅助空间展开/收起、专注模式、Light/Dark、1440px 桌面、窄屏/移动端。
- 所有关键操作可键盘到达，按钮有可访问名称；保存错误与冲突须使用明确的 `role=alert` 或等效可访问反馈。

### 数据、接口与验收

- 复用 `Workspace`、`Chapter`、布局偏好和章节加载接口，不要求新增 API。
- 首次布局不能覆盖已保存偏好；无正式章节时说明如何由作者加入章节，不生成内容。
- 1440px 打开作品后正文是主要注意力区域；章节切换可直接发现；作者显式打开面板后可访问已有功能；刷新后保存的偏好仍生效。

## 任务 2：续写入口与作者计划

### 当前体验问题

- 产品会恢复上次的章节，但没有将作者的“下次写什么”与 AI 推测分开的入口。
- 当前没有可靠依据显示作者计划；不得把 AI 猜想写成作者计划。

### 建议用户流程

打开作品 → 显示“上次写到”章节与一小段真实末尾原文 → 如作者曾写下“下次要写”，原样展示 → 作者选择“继续写”或“先想一想”。没有作者计划时不显示猜测性建议。

### 页面/组件结构

- 可作为写作首页中的轻量“继续上次”卡片，不另造复杂 Dashboard。
- 最近章节标题、真实原文摘录（截断标记清楚）、作者笔记、最多三条证据明确关联当前章的未决事项。
- 提供关闭/收起机制，避免每次打开都阻塞正文。

### 交互状态

- 首次使用、已有上次章节、没有章节、没有作者计划、计划已过期、关联事项来源失效、加载失败。
- “继续写”打开原章节；“先想一想”打开思考空间，并把可追溯的章节/笔记上下文带入，不自动调用 LLM。

### 数据、接口与验收

- 数据：`lastChapterId`、最新已确认正文版本及 Markdown 摘录、作者填写的 `nextWritingNote`、最多三条有可核验来源的相关事项。
- 可能需要 Workspace State 扩展和 Note/Issue 查询；先确认 Note 的存储方式，不在 UI 中以假数据填充。
- 只有作者的原始计划被展示为计划；没有计划时展示空状态。验收应使用隔离的 API fixture 和空项目 fixture。

## 任务 3：随手笔记与定稿变更边界

### 当前体验问题

- Demo 可将对话/推演直接保存为提案；Proposal 是正式候选变更记录语义，容易成为第二个收件箱。
- 当前 API 没有 Note 和 Canon Change 写入流程，不能把 Demo 行为当成真实能力。

### 建议用户流程

随手记录 Note（可未完善、可矛盾、非事实）→ 作者继续思考 → 作者明确选择是否整理成设定变更 → 展示 before/after、证据和影响 → 作者逐项确认 → 记录决定并走正式 Harness 更新流程。

### 页面/组件结构

- 轻量“记一笔”输入，默认绑定当前作品，可选绑定章节或引用。
- Note 列表与正式“待确认变更”分开；不同标题、空状态和筛选，不共用待办徽标。
- Canon Change 详情展示字段差异、来源、影响对象、来源是否过期、作者逐项决定。

### 交互状态

- 草稿、已保存 Note、Note 与章节绑定、转换前确认、候选差异、部分接受、来源过期、版本冲突、存储失败、作者确认结果。
- 任何“确认”动作须明确它会更新正式知识；拒绝/暂缓不会改正文或已确认设定。

### 数据、接口与验收

- `AuthorNote`: noteId、projectId、text、可选 chapterId/sourceQuote/sourceHash、author、时间、状态；绝不自动作为 Canon。
- `CanonChangeProposal`: proposalId、target、before/after、baseVersion/sourceHash、evidence、impact、item decision、作者决定和审计。
- 候选 API 可能包括 Note CRUD、Canon Change Proposal 创建/详情/决定；必须等产品和 OpenAPI 审定后再实现。
- 验收：普通对话/推演不会自动变成正式提案；新 Note 不出现在“已确认设定”；作者确认前正式资料哈希不变；过期证据禁止静默应用。

## 任务 4：页边注记与正文锚点

### 当前体验问题

- Demo 注记使用段落序号和 quote；插入/移动段落后可能错位，API 没有真实持久化或真实审查。
- 作者需要知道发现具体依据在哪一段，同时不应在每次输入时被打断。

### 建议用户流程

作者主动审查 → Agent 读取固定章节版本与有限来源 → 生成候选发现 → 验证证据 → 作者打开时定位原文 → 选择查看/暂缓/标记有意变化/进入候选变更；任何操作都不替换正文。

### 页面/组件结构

- 默认不显示注记数量红点；正文旁的轻量锚点仅在作者查看注记时出现。
- 注记详情显示：原文摘录、证据 A/B、事实与推断分组、来源版本、校验状态、作者操作。
- 可从注记跳转正文并提供“返回原位置”。窄屏时转为抽屉/底部面板。

### 交互状态

- 收起、展开、当前正文锚定、引用已过期、引用被删除、引用匹配歧义、部分证据缺失、审查覆盖不全、Agent 失败/取消、正文版本变化导致旧结果丢弃。
- 锚点唯一匹配、上下文重定位成功、重定位歧义、找不到引用时，必须明显区分；歧义不能自动选中近似内容。

### 数据、接口与验收

- `Finding`: projectId、chapterId、revisionId、contentHash、reviewRunId、scope、事实/推断、evidenceRefs、作者状态、createdAt。
- `EvidenceRef`: source path/ID、sourceHash、精确 quote、可选前后文、精确范围、availability。
- 锚点候选策略：版本 Hash + 精确 quote + 前后文；编辑器位置仅作为展示加速信息。若有多处匹配/无匹配/Hash 已过期，必须标为歧义/失效，禁止悄悄跳转错段。稳定 block ID 的实现方式需结合 TipTap/Figma原型评估，不能只依赖段落序号。
- API 需要显式审查任务、结果持久化/查询、证据解析；不在本阶段假装这些端点已存在。
- 验收：插入/删除/移动段落后能正确定位或显示失效；注记不改变 Markdown；修改正文后旧审查结果不应用到新 Hash；所有显示为已核验的引文与源文件精确一致。

## 任务 5：本章相关知识视图

### 当前体验问题

- Demo 知识更像静态百科目录；真实 API 当前没有 Knowledge API。不能把语义相似当成真实设定关系。

### 建议用户流程

作者在当前章节写作 → 主动打开“本章相关” → 先看明确关联人物、确认规则、可追溯伏笔 → 查看来源原文和状态 → 可进入全量“书”空间。

### 页面/组件结构

- 当前章节相关分组：人物、已确认世界规则、相关伏笔。每组最多五条，提供“查看全部”。
- 每条展示简短摘要、确认/待确认状态、明确关系来源入口；推测关联需单独标明，不能和已确认知识混排。

### 交互状态

- 已有明确关联、没有相关条目、当前章节未知、关系仅为候选推断、来源过期、投影/检索不完整、API 不可用。
- 不可用时如实说明尚未接入，不显示 Demo 条目。

### 数据、接口与验收

- 查询上下文：projectId、chapterId、revisionId/contentHash；来源：章节引用、确认的关系边、knowledge sourceHash、状态、明确推断标记。
- 最小查询接口须能返回 source refs、确定性关系类型、匹配理由和 coverage；仅由 LLM 推断的关联必须单独标记，不得伪装成确认事实。
- 可能需要 Knowledge Query API、Source Viewer 和 DTO Mapper；先出 OpenAPI 差异再实现。
- 验收：每项可追溯到原始资料；确认与推断视觉/语义分明；未知/无数据空态真实；全量知识作为二级入口保留。

## 任务 6：故事内容冲突的证据对照

### 当前体验问题

- HTTP 409 是两个编辑版本的并发冲突；故事冲突是关于情节/人物的待作者判断。二者必须保持独立。
- 当前故事发现卡片可显示证据，但没有原文并排对照和完整判断流程。

### 建议用户流程

证据 A（当前章节）+ 证据 B（历史章节/确认资料）→ AI 说明“可能不一致”及不确定性 → 作者选择人物成长、有意为之、修改正文或候选设定变更。

### 页面/组件结构

- 两段原文并排或上下展示，中文引用清晰可读；每段显示章节/资料来源和版本有效性。
- AI 推断与原文事实分区；“故事内容冲突”不得复用“版本冲突”颜色/标题/错误码。
- 正文修改动作只导航到编辑器及定位，不给 AI 文本替换按钮；设定修改仅进入 Canon Change 候选流程。

### 交互状态

- 两条证据均有效、一个来源过期、原文缺失、引用不唯一、作者标记有意、准备修改正文、准备提案、暂不判断、版本 409 并发冲突。
- 每个作者操作需要说明对 Note、发现状态、正式设定和正文是否有副作用。

### 数据、接口与验收

- 两个 EvidenceRef、Finding ID、来源 Hash、审查 run/revision、作者选择和可选理由。
- 不直接调用正文写入或 Harness 正式知识写入 API。记录故事判断与接受正式知识变更应为两个操作。
- 验收：原文 A/B 可导航和核验；409 页面继续保留本地 Markdown；“修改正文”只打开编辑器；“修改设定”只创建候选，不更改 book。

## 任务 7：变更历史与内部 ID 隐藏

### 当前体验问题

- 稳定 ID、source hash、Git revision 有重要审计用途，但不应成为写作主界面信息。
- 正式知识变更尚未实现完整作者逐项确认流程。

### 建议用户流程

作者从作品资料进入一条设定 → 阅读当前内容/来源 → 查看“变更记录” → 展开某次作者确认前后差异 → 可返回候选/决定和证据。

### 页面/组件结构

- 默认展示作者语言：作品资料、确认设定、创作笔记、修订历史、来源。
- 在“详细信息/调试信息”中显示稳定 ID、Hash、路径和内部 revision；不要删字段或变更 ID。
- 变更历史按发生时间和父子版本关系明确排序，区分作者确认、系统导入和 Agent 候选。

### 交互状态

- 尚无历史、单条、多个版本、来源缺失、候选未决定、部分项目应用失败、版本过期/冲突、仅开发调试字段展开。

### 数据、接口与验收

- 复用 Knowledge Version、Decision、Audit、sourceHash 和 Harness path；显示字段要适配中文作者语言。
- 暂不要求新增存储；若版本缺少明确父子关系，不以 UI 排序掩盖数据问题。
- 验收：默认写作页不展示技术 ID；详细信息可追溯；正式更新能看到变更前后、依据、影响和作者决定。

## 任务 8：中文长文本视觉系统和响应式

### 当前体验问题

- Claude 评审对卡片/边框密度、字号和阅读宽度的判断没有真实截图证据。
- 当前 Figma Token 是权威，Codex 不应因口头建议直接批量替换 Tailwind 样式。

### 建议用户流程 / 结构

- 在当前真实原文长度下比较纯稿纸、章节上下文和辅助面板；测试 1440px、常见笔记本宽度和窄屏。
- Figma 明确哪些边界属于可见工作区、编辑器纸面、注记高亮和浮层；保持正文周围留白服务阅读，不为追求“极简”破坏导航可发现性。

### 交互状态、数据与验收

- Light/Dark、focus、左右栏开关、长标题、较长中文段落、Markdown 引用/列表、焦点键盘态、错误/冲突/恢复态。
- Figma 管理 token：字体族、正文尺寸/行高、中文行宽、颜色语义、间距、边框、圆角、阴影。
- 建议评估而非预设：正文字号、阅读行宽和卡片密度。具体数值由 Figma 基于真实文本确认。
- 验收：提供 1440px Light/Dark/Focus 截图与小屏截图；工程只更新对应 tokens/组件；以真实 Figma 画面做差异列表，不改无关业务状态。

## Note、思考和正式变更的数据边界建议

以下是 Figma/产品讨论用数据图，不是已落地的存储或接口：

```text
Author Note ──(作者明确发起)──> Canon Change Candidate
   │                                   │
   ├─可绑定章节/摘录                    ├─before / after
   ├─非正式/允许矛盾                    ├─sourceHash / baseVersion
   └─不更新 book/                       ├─evidence / impact
                                       └─逐项作者决定 + Audit
```

保存 Note 仍为应用草稿或作者明确导出的 Markdown 记录；作品正式事实只有作者确认的知识变更可进入相应 Harness 记录。普通 chat、推演和 AI 发现都不自动进入上述箭头。

## Figma 交付与工程验收

请将以下资料交给 Codex 后再实现：

1. 选定 IA 与未选方案的理由、作者验证假设。
2. 每个新页面/组件的 Figma 节点链接和完整组件状态。
3. Light/Dark、1440px 桌面、窄屏、专注、展开/收起和空/错误/过期状态画面。
4. Design Tokens 的变更清单；不得只附拼图或静态截图。
5. 设计中使用的字段与真实 API 能力映射；尚未有 API 的内容标为“未来/演示”，禁止伪装已接入。
6. 对 Note、Canon Change、故事冲突各作者动作的副作用说明。

工程实现顺序：

1. 在新工作分支从最新 `main` 更新；确认 Harness、创作数据和工作流差异。
2. 重新通过 Figma MCP 读取交付节点及源码，记录读取时间、节点和 Design Token 变化。
3. 将设计组件映射到现有 React 组件，先列受影响文件及交互状态；保持当前 409、保存、Markdown 和恢复机制不变。
4. 先更新可复用 Token / 展示组件，再接 API DTO / hooks / services；没有后端实现时使用明确标记的 Demo Adapter 或真实空状态。
5. 为新增状态补单元/交互测试；检查保存错误、409、章节切换和本地恢复。
6. 在 1440px 下运行 Light、Dark、Focus 和窄屏画面；Figma 可取图时逐项比较结构、字体、色彩、间距和状态。
7. 增量提交同步记录。不得通过整体覆盖应用目录完成同步；不得改写 `book/`、`manuscript/` 或未获作者确认的正式设定。

## 下一阶段 Agent 设计边界

建议独立 Sprint 做一次作者主动触发的“人物事实 + 时间线”连续性审查：

```text
作者主动触发
  → 固定当前章节 revisionId/contentHash
  → 读取有限、带来源 Hash 的 Harness 证据
  → 真实 LLM 生成结构化候选发现
  → 校验每条引用和 coverage
  → 以注记定位到当前正文
  → 作者判断；不写正文、不更新 book/
```

- 不在输入过程中自动调用模型；未获作者明确模型配置/触发，不发送未发表正文到第三方。
- 结果绑定来源版本；旧版本或失效证据不可静默套用。
- Agent 不暴露 shell、文件系统写入、Git 或 Harness 修改工具。
- 普通发现不自动转换为 Proposal/Canon Change；作者需要明确“整理为正式变更”后才走差异审批。
